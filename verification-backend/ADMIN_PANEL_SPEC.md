# Admin Panel Spec

## Overview

The admin panel is a password-protected web UI served directly by the Cloudflare Worker.
It lets an admin view, filter, edit, add, and delete certificate records stored in D1.

No extra infrastructure is needed. The Worker serves both the public verify pages and the
private admin panel from the same deployment.

---

## Two-Key System

| Key | Name | How it is set | What it unlocks |
|-----|------|---------------|-----------------|
| `API_KEY` | Generation key | `wrangler secret put API_KEY` | `POST /api/batch-save` — used by CertiMaster frontend when generating certificates |
| `ADMIN_KEY` | Admin key | `wrangler secret put ADMIN_KEY` | `POST /admin/login` and all `/admin/api/*` routes — used only inside the admin panel |

The two keys are completely independent. A person who has the API key can save certificate
records but cannot read, edit, or delete them. The admin key gives full read-write access
to the admin panel but cannot be used to call the generation endpoint.

Both keys are set as encrypted Cloudflare Worker secrets — they are never visible after
being set and are never returned in any response.

---

## D1 Schema

One new table is added alongside the existing `certificates` table.

```sql
CREATE TABLE IF NOT EXISTS certificates (
  id    TEXT PRIMARY KEY,   -- UUID generated by CertiMaster frontend
  name  TEXT NOT NULL,      -- Recipient name
  event TEXT NOT NULL,      -- Event name
  date  TEXT NOT NULL       -- Event date (YYYY-MM-DD)
);

CREATE TABLE IF NOT EXISTS login_attempts (
  ip           TEXT PRIMARY KEY,  -- CF-Connecting-IP header value
  attempts     INTEGER NOT NULL DEFAULT 0,
  locked_until TEXT,              -- ISO timestamp; NULL means not locked
  last_attempt TEXT               -- ISO timestamp of most recent attempt
);
```

The `login_attempts` table only holds one row per IP. Rows are upserted on every
`/admin/login` call and cleaned up on successful login.

## Routes

### Public routes (no auth)

#### GET /verify/:id
- Auth: none
- Returns: HTML page showing whether the certificate is valid or not
- On found: green "Verified Authentic" page with name, event, date, id
- On not found: red "Certificate Not Found" page

---

### Generation route (API_KEY required)

#### POST /api/batch-save
- Auth: `Authorization: Bearer <API_KEY>` header
- Body: JSON array
  ```json
  [
    { "id": "uuid-v4", "name": "Alice", "event": "Hackathon 2026", "date": "2026-03-11" },
    { "id": "uuid-v4", "name": "Bob",   "event": "Hackathon 2026", "date": "2026-03-11" }
  ]
  ```
- Success response `200`:
  ```json
  { "success": true, "saved": 2 }
  ```
- Error responses:
  - `401` `{ "error": "Unauthorized" }` — missing or wrong API_KEY
  - `400` `{ "error": "Body must be a non-empty array" }` — wrong body shape
  - `400` `{ "error": "Invalid JSON" }` — unparseable body

### Admin login

#### POST /admin/login
- Auth: none (the password IS the body)
- Body:
  ```json
  { "password": "your-admin-key" }
  ```

**Brute-force protection — evaluated before the password is checked:**

1. Extract IP from the `CF-Connecting-IP` header (set by Cloudflare on every request).
2. Look up the IP in `login_attempts`.
3. If `locked_until` exists and is still in the future:
   - Return `429` immediately. Do not check the password at all.
   - Response:
     ```json
     { "error": "Too many failed attempts. Try again after 2026-03-11T10:30:00.000Z" }
     ```
4. If `locked_until` is in the past, treat the row as if attempts = 0 (lockout expired).

**After the lockout check, validate the password:**

- If password is **wrong**:
  - Increment `attempts` by 1, update `last_attempt` to now.
  - If `attempts` reaches **5**: set `locked_until = now + 15 minutes`.
  - Return `401`:
    ```json
    { "error": "Invalid password", "attempts_remaining": 2 }
    ```
    (Field `attempts_remaining` = `5 - new_attempts`. Omitted once locked.)
  - If now locked, return `429`:
    ```json
    { "error": "Too many failed attempts. Try again after 2026-03-11T10:30:00.000Z" }
    ```

- If password is **correct**:
  - Delete the IP row from `login_attempts` (reset the counter).
  - Issue a session token.
  - Return `200`:
    ```json
    { "token": "<signed-session-token>" }
    ```

**Lockout parameters (constants in Worker code):**

| Constant | Value | Meaning |
|----------|-------|---------|
| `MAX_ATTEMPTS` | 5 | Failed attempts before lockout |
| `LOCKOUT_MINUTES` | 15 | How long the IP is locked after hitting the limit |

These are defined at the top of `index.js` so they are easy to change.

**Why per-IP and not per-session?**
The login endpoint is stateless and has no session before login. The only stable identifier
available before a token is issued is the source IP. `CF-Connecting-IP` is injected by
Cloudflare's edge — it cannot be spoofed by the HTTP client.

Session token format (dot-separated, base64url):
```
base64url(payload_json) . base64url(hmac_sha256_signature)
```
Payload JSON:
```json
{ "role": "admin", "exp": 1741699200 }
```

The Worker verifies the HMAC on every admin API request. No external JWT library needed —
the Web Crypto API (`crypto.subtle`) is available natively in Workers.

### Admin API routes (ADMIN_KEY session token required)

All admin API routes require the header:
```
Authorization: Bearer <session-token>
```
The Worker validates the token signature and expiry on every request.

Error response when token is missing, invalid, or expired:
```json
{ "error": "Unauthorized" }   // 401
```

#### GET /admin/api/records
List records with optional filters.

Query parameters (all optional):

| Param | Type | Example | Description |
|-------|------|---------|-------------|
| `event` | string | `Hackathon 2026` | Case-insensitive substring match on `event` |
| `name` | string | `Alice` | Case-insensitive substring match on `name` |
| `date` | string | `2026-03-11` | Exact match on `date` |
| `date_from` | string | `2026-01-01` | Records with date >= this value |
| `date_to` | string | `2026-12-31` | Records with date <= this value |
| `page` | integer | `1` | Page number, default 1 |
| `per_page` | integer | `50` | Records per page, default 50, max 200 |

Success response `200`:
```json
{
  "records": [
    { "id": "uuid", "name": "Alice", "event": "Hackathon 2026", "date": "2026-03-11" }
  ],
  "total": 1,
  "page": 1,
  "per_page": 50,
  "total_pages": 1
}
```

### Admin UI route

#### GET /admin
- Auth: none at the HTTP level — the login form is the gate
- Returns: the full admin panel HTML page (single-file, self-contained)
- The page handles its own auth in JS:
  - On load it checks `sessionStorage` for a stored token
  - If token absent or expired, shows the login screen
  - On successful login it stores the token and shows the dashboard
  - All admin API calls attach `Authorization: Bearer <token>`

## Admin Panel UI — Feature List

### Login screen
- Password input + Login button
- On wrong password: inline error "Incorrect admin key"
- On success: token stored in `sessionStorage`, dashboard shown

### Dashboard header
- Total certificates, unique events, unique recipients, latest date
- Sourced from `GET /admin/api/stats`

### Records table
Columns: Name, Event, Date, Certificate ID, Actions (Edit, Delete)

### Filters bar
- Text search: Name (live-filter as you type, debounced 300ms)
- Text search: Event name (same)
- Date picker: exact date
- Date range: From / To
- Clear filters button
- Pagination controls (prev / next / page number display)

### Add record button
Opens an inline form / modal:
- Fields: Name, Event, Date
- Submit calls `POST /admin/api/records`
- On success: record appears in table without full page reload

### Edit record (per row)
- Clicking Edit turns the row into an inline editable form
- Fields: Name, Event, Date (ID is read-only, shown as non-editable)
- Save calls `PUT /admin/api/records/:id`
- Cancel restores the row to read-only view

### Delete record (per row)
- Clicking Delete shows an inline "Are you sure? Confirm / Cancel"
- Confirm calls `DELETE /admin/api/records/:id`
- Row removed from table on success without full reload

### Logout button
- Clears `sessionStorage` token
- Returns to login screen

## Security Notes

### Attack surfaces

There are only two places where secrets are accepted from the outside:

| Endpoint | Secret accepted | Brute-forceable? |
|----------|----------------|------------------|
| `POST /api/batch-save` | Raw `API_KEY` in `Authorization` header | Yes — but this endpoint only writes data; it cannot read, edit, or delete records. An attacker who guesses the API_KEY can insert fake certificates but cannot access or destroy existing ones. |
| `POST /admin/login` | Raw `ADMIN_KEY` in request body | Yes — **rate-limited per IP** (5 attempts then 15-minute lockout). |
| All `/admin/api/*` routes | HMAC session token | No — HMAC signatures cannot be guessed; you must have gone through `/admin/login` first. |

### Brute-force mitigation details

1. **Rate limiting on `/admin/login`**: 5 wrong passwords from the same IP triggers a
   15-minute lockout stored in the `login_attempts` D1 table. The Worker reads this table
   before even checking the password, so a locked IP is rejected immediately with `429`.

2. **`CF-Connecting-IP` as the identifier**: This header is set by Cloudflare's edge and
   cannot be forged by the HTTP client. It is the most reliable IP identifier available
   without additional infrastructure.

3. **Token expiry**: Session tokens expire after 8 hours. Even a stolen token becomes
   useless after that window.

4. **HMAC integrity**: Tokens are signed with HMAC-SHA256 using `ADMIN_KEY`. Any
   modification to the token payload (e.g. extending the expiry) invalidates the signature.
   The Worker rejects tampered tokens with `401`.

5. **Secrets never returned**: `API_KEY` and `ADMIN_KEY` are never included in any
   Worker response. The session token contains only `{ role, exp }` — no key material.

6. **Successful login resets the counter**: The IP row in `login_attempts` is deleted on
   a correct password, so a legitimate admin who previously had failed attempts starts
   fresh after logging in successfully.

## Setup Steps (for new deployments)

```bash
# 1. Set both secrets
wrangler secret put API_KEY      # paste generation key when prompted
wrangler secret put ADMIN_KEY    # paste admin key when prompted

# 2. Create D1 database (if not done yet)
wrangler d1 create certimaster-db

# 3. Apply schema
wrangler d1 execute certimaster-db --file=schema.sql

# 4. Deploy
wrangler deploy
```

After deployment:
- Admin panel: `https://your-worker.workers.dev/admin`
- Verify URL: `https://your-worker.workers.dev/verify/<uuid>`
- Generation endpoint: `POST https://your-worker.workers.dev/api/batch-save`
